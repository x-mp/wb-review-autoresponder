# Спецификация WB Review Assistant

Версия: 1.0 draft · дата проверки источников: 7 августа 2026 года

## 1. Цель и границы

Сервис уменьшает время ответа продавца, повышает качество коммуникации и превращает отзывы/вопросы в продуктовые и коммерческие сигналы. Он не накручивает отзывы, не выдаёт неподтверждённые обещания и не гарантирует удаление негатива. Жалоба применяется только к вероятному нарушению правил; обычное субъективное недовольство обрабатывается корректным ответом и внутренней аналитикой.

MVP работает только с Wildberries и одним кабинетом. PostgreSQL является единственной control-plane БД. Следующая версия: несколько кабинетов, RBAC, durable queue, метрики Prometheus и уведомления.

## 2. Пользовательские сценарии

1. Worker получает все карточки, неотвеченные и отвеченные вопросы/отзывы и архивные отзывы.
2. Оператор видит обращение, товар, оценку, текущий статус и подтверждённые факты.
3. Policy engine назначает цель, затем OpenRouter возвращает структурированный черновик.
4. Валидатор блокирует контакты, верхний регистр, чрезмерную пунктуацию, низкую уверенность и рискованные темы.
5. Оператор редактирует/одобряет. Только явно включённый write-контур делает read-before, публикует и делает read-back.
6. Для негативного отзыва сервис отдельно оценивает критерии жалобы, собирает доказательства и вопросы оператору, готовит текст до 1000 символов. Отправка — вручную в кабинете WB.

## 3. Цели ответа и бизнес-задачи

| Цель | Применение | Бизнес-результат |
|---|---|---|
| `answer_factually` | характеристика/комплектация | точный ответ |
| `support_conversion` | вопрос перед покупкой | помощь в выборе без давления |
| `prevent_wrong_purchase` | размер/совместимость/ограничение | меньше возвратов |
| `thank_and_reinforce` | 4–5 звёзд | лояльность, повторная покупка |
| `deescalate` | 1–3 звезды | снижение конфликта |
| `recover_service` | подтверждённая проблема | корректный следующий шаг |
| `reduce_uncertainty` | фактов не хватает | не допустить выдумку |
| `surface_product_issue` | повторяемый дефект | улучшение товара/карточки |
| `growth_opportunity` | частый запрос новой функции/варианта | ассортимент и допродажа |

Допродажа разрешена только если релевантный товар и факт присутствуют в каталоге, не подменяет ответ на вопрос и не используется в негативной/рисковой ситуации.

## 4. Компоненты

```text
WB Questions/Feedback API ----> worker ----> raw archive (append-only)
WB Content API ---------------/    |                |
                                      v                v
                                  PostgreSQL <---- manifests
                                      |
                         policy + product retrieval
                                      |
                               OpenRouter draft
                                      |
                        FastAPI UI -> approve -> write guard
                                                  |
                                      read-before -> WB -> read-back
```

- `config/methods.json` — проверенный реестр источников и лимитов.
- `wb.py` — только зарегистрированные API-вызовы и rate limit.
- `artifacts.py` — неизменяемые raw response + manifest.
- `service.py` — нормализация и workflow.
- `policy.py` — детерминированные ограничения и жалобы.
- `llm.py` — OpenRouter, JSON schema, redaction.
- `web.py` — защищённая панель/API.

## 5. Контракт данных

Raw: `data/raw/<source>/<entity>/<YYYY>/<MM>/<DD>/<run_id>/response.*` и `manifest.json`. Нормализованные записи всегда содержат `source_run_id`; raw-ответ — источник истины. Курсор можно продвигать только после сохранения raw и успешной транзакции. Токены и заголовки авторизации не сохраняются.

Основные сущности: `products`, `interactions`, `drafts`, `complaints`, `audit_log`, `access_log`, `sync_state`. Дедупликация обращений — по WB ID, товаров — по `nmID`. `audit_log` хранит все изменения состояния, а `access_log` — все обращения к UI/API, включая неуспешную авторизацию, без секретных значений.

## 6. Безопасность и публикация

- UI/API: постоянновременное сравнение Bearer-токена, HttpOnly/SameSite cookie после `/login`; production cookie — Secure.
- Секреты только через окружение/secret manager; логи и manifest без секретов.
- `AUTO_PUBLISH=false` по умолчанию; только `approved` draft может уйти в WB.
- Перед write: повторное чтение, проверка ID/типа, локальная валидация; после write: read-back и аудит.
- Ответы WB проходят модерацию; редактирование ответа допускается один раз в течение 60 дней. MVP не редактирует опубликованные ответы автоматически.
- Риск `legal_or_safety`, персональные данные, компенсация, возврат денег, травма/пожар — только человек.
- Для production перед интернет-публикацией нужны TLS reverse proxy, ротация токена, rate limiting входа и PostgreSQL/RBAC.

## 7. Нефункциональные требования и приёмка

- Повторная синхронизация идемпотентна и не перезаписывает raw.
- 429 соблюдает `Retry-After` (до production нужно добавить retry/backoff); 401/403 не ретраятся бесконечно.
- Ошибка OpenRouter не приводит к публикации.
- Без `WB_API_TOKEN` demo/UI/tests работают, sync выдаёт явную ошибку без раскрытия секрета.
- Все внешние записи выключены в тестах и demo.
- Приёмка на сервере: `pytest`, `ruff`, `docker compose build`, seed demo, health, auth 401/200, sync с тестовым WB token, генерация OpenRouter, ручное approve, отдельный контролируемый live-тест одной записи.

## 8. План развития

P1: текущий MVP на PostgreSQL. P2: Alembic, durable jobs, RBAC, редактирование текста в UI, фильтры и графики SLA/тональности/тем. P3: embeddings по карточкам и базе знаний, clustering проблем, рекомендации по карточкам/ассортименту, A/B оценка ответов. P4: multi-tenant и дополнительные официальные marketplace adapters.
